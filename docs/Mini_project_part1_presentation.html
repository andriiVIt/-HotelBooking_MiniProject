Mini project part 13
Test design

32 unit tests, one consistent structure

  • xUnit v3 as test framework, Moq as mocking framework
  • Arrange - Act - Assert in every test
  • Names read as a sentence: Method_Scenario_ExpectedResult
  • Constructor creates the mocks and a default hotel with 2 rooms; each test only sets up what it needs
  • Helper SetUpBookings(...) keeps the Arrange part short
  • Dates are relative to DateTime.Today, so tests never expire

How the cases were chosen

Equivalence classes: invalid dates, no bookings, free room, all rooms taken, inactive (cancelled) booking.

Boundary values: the day before, the same day, and the day after an existing booking.

public BookingManagerTests()
{
    rooms = new List<Room> { /* Id 1 and 2 */ };
    mockBookingRepository = new Mock<IRepository<Booking>>();
    mockRoomRepository    = new Mock<IRepository<Room>>();
    mockRoomRepository.Setup(r => r.GetAllAsync())
                      .ReturnsAsync(rooms);
    bookingManager = new BookingManager(
        mockBookingRepository.Object,
        mockRoomRepository.Object);
}
Mini project part 14
Mocking framework

Moq replaces the database, so the tests test only the logic

Stubbing - control the input

Setup(...).ReturnsAsync(...) decides which bookings and rooms the manager sees. No database, fast and deterministic.

Verification - check the interaction

Verify(..., Times.Once) and Times.Never prove that AddAsync is called when a room is free, and not called when the hotel is full.

// CreateBooking: room is free
SetUpBookings();
var booking = new Booking {
    StartDate = Today.AddDays(1),
    EndDate   = Today.AddDays(2) };

await bookingManager.CreateBooking(booking);

mockBookingRepository.Verify(
    r => r.AddAsync(booking), Times.Once);

// CreateBooking: all rooms taken
mockBookingRepository.Verify(
    r => r.AddAsync(It.IsAny<Booking>()),
    Times.Never);

[Theory]
[MemberData(nameof(FullyOccupiedDatesCases))]
public async Task GetFullyOccupiedDates_
    VariousBookingConfigurations_ReturnsExpectedDates(
    Booking[] bookings, DateTime start,
    DateTime end, DateTime[] expectedDates)
{
    // Arrange
    SetUpBookings(bookings);

    // Act
    List<DateTime> occupied =
        await bookingManager
            .GetFullyOccupiedDates(start, end);

    // Assert
    Assert.Equal(expectedDates, occupied);
}
Mini project part 17
Bugs found by the tests

Bug 1: bookings were counted instead of rooms

GetFullyOccupiedDates compared the number of bookings on a date with the number of rooms.

Example: 2 rooms, and two active bookings on room 1 for the same days. The code counts 2 bookings, 2 ≥ 2, and reports the dates as fully occupied. Room 2 is actually free.

Regression test

// both bookings on room 1, room 2 is free
SetUpBookings(
  new Booking { RoomId = 1, IsActive = true, ... },
  new Booking { RoomId = 1, IsActive = true, ... });

var result = await bookingManager
    .GetFullyOccupiedDates(start, end);

Assert.Empty(result);

Step 1 - the test fails on the old code RED

The method returned every date from day 5 to day 10 instead of an empty list.

Step 2 - the fix GREEN

// OLD (bug)
// if (noOfBookings.Count() >= noOfRooms)

// FIXED: count each booked room once
if (noOfBookings
      .Select(b => b.RoomId)
      .Distinct()
      .Count() >= noOfRooms)
    fullyOccupiedDates.Add(d);

After the fix all 32 tests pass.

Mini project part 18
Bugs found by the tests

Bug 2: off-by-one in the overlap check

In FindAvailableRoom a comparison used <= where it needed <.

// wrong: request ending ON the existing
// start date looked like "no overlap"
startDate <= b.StartDate && endDate <= b.StartDate

// correct
startDate < b.StartDate && endDate < b.StartDate

Why the data-driven test catches it

The case { 1, 10, false } asks for a stay that ends exactly on the day the existing booking starts. With <= the room is wrongly returned as free, so the assertion fails.

A single "typical" test would never hit this edge. This is why boundary values are worth a theory.

Mini project part 111
Conclusions

What we learned

  • Dependency injection is what makes the code testable: repositories are interfaces, so Moq can replace them.
  • Mocks give speed and control; Verify checks behaviour, not only return values.
  • Data-driven tests turn boundary analysis into a compact table of cases.
  • Tests found two real bugs: the wrong count and the off-by-one comparison.
  • Write the failing test first, then fix: red, green, and the test stays as a regression guard.
  • Static analysis and coverage tell us where to look; well-chosen inputs tell us if it is right.
